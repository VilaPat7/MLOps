Kubernetes (часто называют «k8s») — это система для автоматизации развертывания, масштабирования и управления контейнеризированными приложениями. Представьте, что у вас есть несколько микросервисов (например, веб‑сервер, база данных, модель машинного обучения), каждый из которых упакован в контейнер (Docker). Вам нужно, чтобы эти контейнеры запускались, общались друг с другом, восстанавливались при сбоях, масштабировались при нагрузке. Всем этим занимается Kubernetes.

Основные понятия Kubernetes
Под (Pod) — самая маленькая единица в Kubernetes. Это группа из одного или нескольких контейнеров, которые разделяют сетевые ресурсы (один IP‑адрес) и хранилище. Обычно под содержит один главный контейнер (ваше приложение) и, возможно, вспомогательные (например, sidecar‑прокси для сетевого взаимодействия, как Istio proxy). В ваших примерах вы видели поды с контейнерами preprocessor, tf-serving, istio-proxy.

Деплоймент (Deployment) — описывает желаемое состояние подов: какой образ контейнера использовать, сколько реплик (копий) пода должно быть запущено, как обновлять их. Если под упадёт, деплоймент создаст новый. Вы редактировали деплоймент ml-pipeline-ui и mlflow-server.

Сервис (Service) — абстракция, которая предоставляет стабильный IP‑адрес и DNS‑имя для доступа к подам. Например, поды могут пересоздаваться и менять IP, но сервис остаётся неизменным. Сервисы обеспечивают внутреннюю связь между компонентами.

Конфигурации: бывают в виде ConfigMap (для текстовых настроек, переменных окружения) и Secret (для чувствительных данных — паролей, ключей). Они монтируются в поды как файлы или переменные окружения.

PersistentVolume (PV) и PersistentVolumeClaim (PVC) — для хранения данных, которые должны сохраняться даже после перезапуска подов (например, базы данных, файлы моделей).

Namespace — виртуальный кластер внутри физического, позволяет разделять ресурсы между командами или проектами (в вашем выводе есть kubeflow-pipelines, mlflow-system, default).

kubectl — главная командная утилита
kubectl — это клиент командной строки для взаимодействия с Kubernetes API. С его помощью вы отправляете команды кластеру: создать объект, посмотреть логи, описать ресурс, применить изменения из файла и т.д. Все ваши команды (kubectl get pods, kubectl describe node, kubectl logs, kubectl edit deployment) — это работа с kubectl.

minikube — локальный кластер для разработки
Minikube — это инструмент, который позволяет запустить однопользовательский кластер Kubernetes на вашем локальном компьютере (в виртуальной машине или Docker). Он идеален для изучения и тестирования, потому что не требует сложной настройки облачных провайдеров. Когда вы запускаете minikube, создаётся одна нода (виртуальная машина), которая играет роль и управляющего узла (control plane), и рабочего узла. Все ваши поды разворачиваются на этой ноде (как minikube в выводе kubectl get nodes).

MinIO — S3‑совместимое объектное хранилище
MinIO — это высокопроизводительное хранилище объектов, которое реализует API, совместимое с Amazon S3. В контексте машинного обучения и Kubernetes MinIO часто используется для:

Хранения обученных моделей, датасетов, артефактов экспериментов.

Работы с MLflow (система управления жизненным циклом ML), которая может сохранять модели в MinIO.

Общего доступа к данным между подами (например, модель, загруженная из MinIO, может быть смонтирована в под tf-serving).

В вашей инфраструктуре MinIO работает как отдельное приложение в кластере (под с именем minio-... в namespace mlflow-system и kubeflow-pipelines). Он предоставляет URL для доступа (например, http://minio.mlflow-system.svc.cluster.local:9000), который используется в переменных окружения (MLFLOW_S3_ENDPOINT_URL).

Как всё это взаимодействует (на примере вашего CIFAR-10)
Сборка образов: Вы создаёте Docker-образы для компонентов (препроцессор, TensorFlow Serving). Они загружаются в реестр (например, Docker Hub) или остаются локально.

Развёртывание в Kubernetes: Вы применяете YAML-файлы с описаниями деплойментов, сервисов, secrets. kubectl отправляет их в API minikube.

Поды запускаются:

Планировщик Kubernetes видит запросы на создание подов, проверяет, есть ли свободные ресурсы на ноде. Если запросы CPU/памяти превышают доступное, под остаётся в состоянии Pending (как у вас с cifar10-inference из-за нехватки CPU requests).

Когда нода найдена, kubelet на ноде (в minikube) скачивает образы и запускает контейнеры.

Инициализация:

Istio‑прокси автоматически внедряется в под (это видно по istio-init и istio-proxy), он настраивает сетевое взаимодействие, безопасность, сбор метрик.

Ваш препроцессор пытается загрузить модель из MLflow и детектор аномалий из pickle-файла. Для этого он использует переменные окружения, которые берутся из secrets (mlflow-secret) и конфигураций.

TensorFlow Serving ожидает модель в /models, которая монтируется через общий volume shared-model (пустой в начале). Препроцессор должен скачать модель и положить её туда, но из-за ошибки с детектором аномалий он падает, и модель не появляется.

Доступ к данным:

Модель может храниться в MinIO. Препроцессор подключается к MinIO по эндпоинту, указанному в секрете, и скачивает модель.

Детектор аномалий — это pickle-файл, который должен либо быть встроен в образ, либо монтироваться из secret или volume. У вас он был пуст (или отсутствовал), что вызвало ошибку загрузки.

Логи и мониторинг:

Вы смотрите логи через kubectl logs, чтобы диагностировать проблему (ошибка EOFError).

Метрики собираются Prometheus (по аннотациям prometheus.io/scrape), визуализируются в Grafana.

Таким образом, Kubernetes координирует все эти компоненты, обеспечивая их сетевое взаимодействие, хранение данных, восстановление при сбоях. Minikube даёт возможность всё это проверить локально, а MinIO предоставляет место для хранения артефактов ML.

Почему возникали проблемы в ваших логах
ImagePullBackOff: Kubernetes не смог скачать образ, потому что репозиторий не существует или недоступен.

CrashLoopBackOff: Контейнер постоянно падает при запуске (как preprocessor из-за ошибки загрузки pickle).

Insufficient cpu: Запрошенных ресурсов CPU больше, чем свободно на ноде.

Readiness probe failed: Прокси проверяет, готов ли контейнер принимать трафик; если он не отвечает или отвечает ошибкой, под считается неготовым.

Понимание этих концепций и инструментов — ключ к успешной эксплуатации приложений в Kubernetes.
