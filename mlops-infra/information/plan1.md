# Подробный пошаговый план реализации системы Security Gates

## Этап 1: Подготовка инфраструктуры и базового решения
**Цель:** Создать среду для экспериментов и базовый пайплайн без защиты.

**Что делать:**
1. Настроить Kubernetes-кластер (например, Minikube или облачный K8s).
2. Установить и сконфигурировать:
   - Kubeflow Pipelines (KFP)
   - MLflow (Tracking Server + Model Registry)
   - KServe (+ Istio для сетевого уровня)
   - Prometheus + Grafana для мониторинга
3. Создать "нулевую конфигурацию" (Baseline):
   - Взять датасет CIFAR-10.
   - Написать стандартный пайплайн обучения CNN в KFP без каких-либо гейтов.
   - Обучить модель, залогировать всё в MLflow, задеплоить модель как простой KServe сервис.
   - **Это ваша "Конфигурация 1" (базовая, без защиты), точка отсчета для сравнения.**

## Этап 2: Разработка компонентов Security Gates (5 штук)
**Цель:** Создать переиспользуемые, независимые компоненты для проверок.

### Пункт A: Создание автономных скриптов (Creating Standalone Scripts)
**Что делать:** Для каждого из первых 5 гейтов (см. ниже) создать отдельный `.py` файл. Каждый скрипт должен:
- Принимать входные данные/аргументы (например, путь к данным, пороговые значения).
- Содержать четкую логику проверки.
- Возвращать понятный код/результат (успех/ошибка) и, возможно, артефакты (например, отчет).
- Быть протестированным локально.

**Примерный список гейтов и их логика:**

1. **Gate 1 (Целостность данных / Data Poisoning Detection):** `validate_data.py`
   - **Что делает:** Анализирует распределение меток/признаков в обучающих данных, ищет статистические аномалии (например, внезапный перекос в одном классе).
   - **Как:** Использует scikit-learn или pandas для расчетов. Сравнивает с базовыми показателями или использует правило "3-х сигм".

2. **Gate 2 (Дифференциально-приватное обучение / Differential Privacy):**
   - **Что делает:** Не отдельный скрипт, а модификация шага обучения. Использует библиотеку типа PyTorch Opacus или TensorFlow Privacy для добавления шума/обрезки градиентов.

3. **Gate 3 (Целостность модели / Model Integrity):** `validate_model.py`
   - **Что делает:** Проверяет, что обученная модель соответствует ожидаемым критериям качества (accuracy > порога) и структуре (например, архитектура, хэш слоев).
   - **Как:** Загружает модель, вычисляет метрики на валидационном сете, сравнивает с конфигурационным порогом.

4. **Gate 4 (Проверка происхождения модели / Model Provenance):** `verify_model_signature.py`
   - **Что делает:** Проверяет цифровую подпись модели перед загрузкой в продакшн.
   - **Как:** Использует библиотеку типа `cryptography`. В пайплайне, после Gate 3, модель подписывается приватным ключом. Этот скрипт проверяет подпись публичным ключом.

5. **Gate 5 (Защита инференса / Adversarial & Input Validation):** `inference_preprocessor.py`
   - **Что делает:** 
     1) Валидирует входящий JSON-запрос через Pydantic (проверка типов, диапазонов).
     2) Пропускает данные через детектор аномалий (например, автоэнкодер) для выявления adversarial-примеров.
   - **Как:** Pydantic для схемы, scikit-learn или TensorFlow для детектора, обученного на "чистых" данных.

### Пункт B: Контейнеризация компонентов (Containerizing Components)
**Что делать:**
1. Для каждого `.py` скрипта из пункта А создать свой Dockerfile.
2. Dockerfile должен:
   - Брать легковесный базовый образ (`python:3.10-slim`).
   - Копировать `requirements.txt` с зависимостями для этого скрипта.
   - Устанавливать зависимости через `pip install`.
   - Копировать сам скрипт и вспомогательные файлы.
   - Определять `ENTRYPOINT` для запуска скрипта.
3. Собрать Docker-образы и запушьте их в Container Registry (например, Docker Hub, Google Container Registry).

### Пункт C: Описание интерфейсов для KFP (Description of KFP interfaces)
**Что делать:**
- Для каждого контейнеризованного компонента (Gate 1, 3, 4) создать YAML-манифест компонента Kubeflow Pipelines.
- В манифесте явно описать:
  - `inputs` (параметры, артефакты) - например, путь к данным, порог accuracy.
  - `outputs` (артефакты) - например, отчет о проверке, подписанная модель.
  - `command` - команду для запуска контейнера с подстановкой входных значений.

## Этап 3: Построение и оркестрация тренировочного пайплайна
**Цель:** Собрать из компонентов безопасный пайплайн обучения.

### Пункт A: Создание скрипта определения графа (Graph definition script)
**Что делать:**
1. Написать Python-скрипт с использованием KFP SDK (`kfp.dsl`).
2. Определить функцию, декорированную как `@kfp.dsl.pipeline`. Внутри неё:
   - Использовать `create_component_from_file` (или подобное) для загрузки YAML-компонентов ваших гейтов.
   - Последовательно соединить шаги: `Загрузка данных -> Gate 1 -> Обучение (с интегрированным Gate 2) -> Gate 3 -> Подписание модели (Gate 4)`.

### Пункт B: Реализация условной логики (Implementing conditional logic)
**Что делать:**
- В том же скрипте пайплайна использовать `kfp.dsl.Condition`.
- **Пример:** `with kfp.dsl.Condition(validation_task.outputs['output_name'] == 'SUCCESS'):` внутри этого блока разместить шаги, которые выполняются только если Gate 1 (или 3) пройден. Иначе пайплайн должен завершиться с ошибкой.

### Пункт C: Интеграция с MLflow (Integration with MLflow)
**Что делать:**
1. В шаг обучения добавить логирование:
   - Параметров (гиперпараметры, параметр ε для DP) -> `mlflow.log_params()`
   - Метрик (accuracy, loss) -> `mlflow.log_metrics()`
   - Обученной модели -> `mlflow.<framework>.log_model()`
2. После успешного прохождения Gate 3, в шаге регистрации модели, зарегистрировать модель в MLflow Model Registry (например, в стадию `Staging`). Использовать `mlflow.register_model()`.

## Этап 4: Создание защищенного сервиса инференса
**Цель:** Создать безопасный эндпоинт для предсказаний.

### Пункт A: Разработка Docker-образа для KServe
**Что делать:**
1. Создать новый Dockerfile для инференса.
2. Написать скрипт-загрузчик модели (`model_loader.py`), который:
   - При старте контейнера обращается к MLflow Model Registry и загружает последнюю продакшен-версию модели.
   - Перед загрузкой выполняет Gate 4 (проверяет цифровую подпись модели).
   - Загружает проверенную модель в память.
3. Написать единый скрипт пре-/пост-процессора (`prepost_processor.py`), который:
   - Реализует Gate 5: валидирует входящий запрос через Pydantic и детектирует аномалии.
   - Если запрос валиден — передает данные на модель для предсказания.
   - Возвращает ответ.
4. Собрать образ и запушьте его в реестр.

### Пункт B: Конфигурация KServe InferenceService
**Что делать:**
1. Создать YAML-манифест `InferenceService`.
2. В манифесте указать созданный вами образ. Настроить `predictor` на использование вашего скрипта-обработчика.
3. Настроить автоскейлинг (`scaleTarget`, `scaleMetric`) и лимиты ресурсов (`limits`, `requests`).

### Пункт C: Настройка аутентификации и авторизации (Gate 6)
**Что делать:**
1. Используя Istio, создать `RequestAuthentication` для вашего эндпоинта, указав `issuer` и `jwks` для проверки JWT-токенов.
2. Создать `AuthorizationPolicy`, которая разрешает доступ только запросам с валидным JWT-токеном.
3. (Опционально) Настроить rate-limiting политики в Istio для защиты от DoS.

## Этап 5: Автоматизация и воспроизводимость
**Цель:** Сделать развертывание системы цельным и повторяемым.

**Что делать:**
1. Написать Shell-скрипты (или Makefile), которые автоматически:
   - Собирают и пушат все Docker-образы.
   - Применяют Helm-чарты для установки KFP, MLflow, KServe и т.д.
   - Загружают конфигурации и манифесты в кластер.
2. Вынести конфигурацию всех гейтов в отдельные `config.yaml` файлы (пороги, пути, ключи). Хранить их в отдельном репозитории (например, Git) и загружать в компоненты при инициализации через volume mounts или переменные окружения.

## Этап 6: Эксперименты и тестирование (Краткий план)
**Цель:** Проверить эффективность и измерить накладные расходы.

**Что делать по порядку:**
1. **Развернуть три конфигурации:**
   - **Конф. 1:** Базовый пайплайн (из Этапа 1).
   - **Конф. 2:** Пайплайн + Инференс с гейтами 1, 3, 4, 5.
   - **Конф. 3:** Полная система со всеми 6 гейтами (включая DP - Gate 2).

2. **Запустить сценарии атак:**
   - **ML02 (Data Poisoning):** Подсунуть "отравленные" данные в Конф.1 и Конф.2. **Ожидание:** Конф.1 обучит плохую модель, Конф.2 остановится на Gate 1.
   - **ML01 (Adversarial Attack):** Сгенерировать adversarial-примеры (через ART) и отправить на инференс Конф.1 и Конф.2. **Ожидание:** Конф.2 блокирует >85% атак благодаря Gate 5.
   - **ML04 (Membership Inference):** Провести MIA-атаку на модели из Конф.1 и Конф.3. **Ожидание:** Атака на Конф.3 неэффективна (accuracy ~50%) благодаря Gate 2 (DP).
   - **ML05 (Model Theft / DoS):** Направить мощный поток запросов на эндпоинт Конф.2. **Ожидание:** Gate 6 (аутентификация, rate-limiting) отклоняет неавторизованные/частые запросы, система стабильна.

3. **Оценить производительность:**
   - Измерить и сравнить время выполнения пайплайна Конф.1 и Конф.2.
   - Измерить и сравнить латентность инференса (p50, p95, p99) у Конф.1 и Конф.2.
   - Для Конф.3 построить график зависимости Accuracy от ε-бюджета (приватности), чтобы увидеть trade-off.

4. **Визуализировать результаты:**
   - Настроить Grafana-дашборды на данных из Prometheus.
   - Вывести на дашборды: графики блокировки атак (ML01, ML05), точность MIA (ML04), накладные расходы на производительность.
   - Провести статистический анализ (t-тест) для подтверждения значимости различий в производительности.
